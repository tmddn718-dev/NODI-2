# NODI v2.0 구현 감사 (Implementation Audit)

- 작성일: 2026-11-16
- 대상: Claude Design 프로젝트 "NODI 서비스 시안" (v1 · v2 · v3 페이지)
- 범위: 「NODI v2.0 — Claude Code 제품 개편 실행 프롬프트」 Phase 0 요구사항

> **핵심 전제** — 이 작업 환경에는 서버 · DB · API를 가진 실제 코드베이스가 없습니다. 현재 NODI의 "코드"는 단일 HTML 디자인 프로토타입입니다. 아래 항목은 이 사실을 기준으로 작성했으며, 서버 측 보장(트랜잭션 · 멱등성 · 버전 관리 · 서버 유효성 판정)은 **구현된 것으로 간주하지 않습니다.**

## 0. 확인 항목별 현황

| 항목 | 현재 상태 |
|---|---|
| 프레임워크/기술 스택 | `.dc.html` 디자인 컴포넌트 1파일 = 마크업 + React 클래스 컴포넌트(`DCLogic`) 런타임. 빌드 도구 · 패키지 없음 |

| 상태 관리 | 컴포넌트 로컬 state 하나. 새로고침하면 초기화 |
| 데이터 모델/저장 | 상수 시드 데이터(PEOPLE, SEED_MEET, SEED_REQ). 영속 저장 없음 |

| 인증/권한 | 없음. 사용자 '정다은' 고정, 공동 관리자 '오민재'는 시나리오 문구 |

| 테스트 환경 | 없음. 자동화 테스트 실행 불가 |

## 1. 현재 구현 기능 (프로토타입 내 동작)

- 자연어 조건 입력 → AI 해석 카드 (항목별 출처 태그: AI 해석 / 직접 수정 / 확인 필요 / 기본값)
- 조건 수정 시트: 날짜·기간, 회의 길이, 시간대, **참석 방식(v3)**, 항목별 '변경됨' 표시
- 참석자 선택 → **역할·성립 정책 설정(v3)**: 일정 필수 참석자 / 일반 참석자, 정책 A(전원 참석 필요) · B(일정 필수 참석자 우선)
- **조율 진행 현황(v3)**: 제출 · 조정하면 가능 · 미응답 · 재확인 필요 집계, 응답 마감, 리마인드(데모), 재확인 요청(데모), 개인정보 안내
- **응답 3축 모델(v3)**: 제출 상태 / 가용성 / 캘린더 상태 분리. 미응답 · 조회 불가 · 조정하면 가능 · 재확인 필요는 가능으로 계산하지 않음
- **응답 유효성(v3)**: 회의 길이 증가 · 참석 방식 변경 시 제출된 응답을 '재확인 필요'로 전환(삭제 안 함). 받은 요청의 후보 변경 시 유지/무효(이력 보존) 구분
- 추천 무효화·재계산(조건 · 참석자 · 역할 · 정책 · 응답 변경 시 키 불일치 → 폐기)
- **포용형 추천(v3)**: 1단계 필수 조건 필터 → 2단계 참여 기회 최대화. 점수와 '확정 가능' 분리, 동률 표시, 일반 참석자 참여 수 표시
- **참여 영향 안내(v3)**: 선택 후보에 참석이 어려운 사람이 있고 모두 가능한 대안이 실제로 있을 때만 안내
- 확정: 재검증 → 기록, 요청 ID 표시. 시나리오 — 응답 변경(중단) · **공동 관리자 동시 확정(v3)** · **네트워크 불명확 → 결과 재조회(v3)**
- **작업별 처리 현황(v3)**: NODI 확정 / 캘린더 / 참석자별 알림을 분리 기록, 실패한 작업만 재시도
- **회의 상태 모델(v3)**: 초안 · 응답 수집 중 · 확정 처리 중 · 확정됨 · 재조율 중 · 취소됨
- **재조율(v3)**: 기존 일정 유지 중 · 새 시간 조율 중, 후보별 응답 유지/재확인, 4단계 변경 확정, 실패 시 기존 일정 유지
- **응답 제출 안정성(v3)**: 임시 저장 표시, 제출 ID, '전송 결과를 확인하고 있어요', '기기에 저장됨 · 아직 제출되지 않음'
- AI 말풍선 가독성 개선: `#DDE4EF` 회색 배경 → `#FFFFFF` + `#DDE4EF` 테두리

## 4. 기술적 위험

1. **서버 보장 부재** — 현재 화면의 중복 방지 · 충돌 처리는 연출입니다. 실제 서비스에서는 서버 멱등성 키 + 회의 버전 낙관적 잠금이 없으면 중복 확정이 발생할 수 있습니다.
2. **캘린더 '충돌 없음'의 과대평가** — 캘린더 기반 참여 가능을 점수에 반영하면 실제 불참이 늘 수 있습니다. 가중치 검증 필요.
3. **재확인 규칙의 과잉/과소 적용** — 현재는 길이 증가 · 참석 방식 변경 시 '모든 제출 응답'을 재확인 처리합니다. 실제로는 영향받는 후보 단위로 판정해야 합니다.
4. **시간대** — 문자열 기반 시각 표기라 실제 시점 변환 오류를 검출할 수 없습니다.
5. **개인정보** — 조정 메모 공개 범위 · 캘린더 권한 범위는 문구만 있고 접근 제어가 없습니다.
6. **단일 파일 구조** — 화면 · 로직 · 데이터가 한 파일에 있어 실제 앱으로 옮길 때 분리 작업이 필요합니다.

## 7. 실제 연동 없이 검증 가능한 범위

- 추천 필터·점수·확정 가능 판정 (결정론적 함수 단위 테스트 가능)
- 응답 상태 → 계산 규칙 매핑 (미응답·조회 불가·조정하면 가능 미계산)
- 조건 변경 → 추천 무효화 · 재확인 대상 판정
- UI 상태 전이 (로딩 · 오류 · 충돌 · 부분 실패 · 재시도 · 재조율 실패)
- 문구 · 접근성(역할 · 라벨 · 상태 메시지) 검토

검증할 수 없는 범위: 실제 중복 요청 처리, 동시성, 네트워크 단절 후 서버 상태, 캘린더·알림 결과, 다중 기기 동기화, 시간대 변환.

## 실행 결과 보고 (프롬프트 18항 형식)

**A. 구현 완료** — 1장 목록 참조. 수정 파일은 5장. 핵심 로직: `slot()`(응답 3축 → 시간대별 상태), `recheckIds()`(응답 유효성), `computeRecs()`(2단계 포용형 추천), `confirm()`(재검증·충돌·결과 재조회), `taskRows()/retryCal()/retryNotify()`(작업별 결과·실패만 재시도).

**B. 검증 결과** — 실행한 자동화 테스트: 없음(테스트 환경 없음). 화면 렌더링 확인: 하지 않음. 16개 필수 테스트의 프로토타입 확인 방법은 v3 페이지 오른쪽 표에 정리. 모든 항목 **미검증**.

**C. 미구현 항목** — 2장 참조. 필요 외부 API: 캘린더(Google/Microsoft) free/busy · 이벤트 쓰기 권한, 이메일/푸시 발송, 인증(OIDC), AI 모델 API.

**D. 위험 및 제한사항** — 4장 참조. 알려진 제한: 재확인 판정이 응답 단위가 아닌 전체 단위, 시간대 미처리, 시드 데이터 고정.

**E. 다음 개발 우선순위** — ① 실제 저장소·서버 스택 확정 후 회의/응답 스키마와 확정 API(멱등성 키 + 버전) 구현 ② `computeRecs` 규칙을 서버로 이전하고 단위 테스트 작성 ③ 외부 작업 큐 + 작업별 결과 테이블 ④ PRD 확정 규칙과 '캘린더 충돌 없음' 가중치에 대한 사용자 검증(주최자 5명, 참석자 5명 인터뷰).
