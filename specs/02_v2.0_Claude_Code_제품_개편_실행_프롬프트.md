# NODI v2.0 — Claude Code 제품 개편 실행 프롬프트

**문서 유형:** Claude Code 실행 프롬프트  
**프로젝트:** NODI — Better timing, together.  
**목표:** VOC 기반 포용형·신뢰형 AI 회의 일정 조율 서비스 개편  
**우선순위:** P0 안정성 → 핵심 UX → 자동화 확장

---

## 1. 역할과 작업 목표

당신은 NODI 프로젝트를 담당하는 시니어 프로덕트 디자이너이자 풀스택 엔지니어입니다.

기존 코드베이스와 PRD를 분석한 뒤, NODI를 단순한 AI 회의 시간 추천 서비스에서 **참석자의 참여 기회를 배려하고, 변경과 오류 상황에서도 회의를 안전하게 확정할 수 있는 AI 일정 조율 서비스**로 개선해주세요.

이번 작업은 전면적인 시각적 리디자인이 아닙니다.

기존 NODI의 브랜드와 UX 방향은 유지하되, 실제 회의 조율 과정에서 발생하는 문제를 해결하는 데 집중합니다.

### 최종 제품 정의

> NODI는 참석자의 일정과 응답을 AI로 조율하고, 모든 참석자의 참여 기회를 최대한 고려하며, 변경과 오류 상황에서도 담당자가 안전하게 회의를 확정하고 관리할 수 있도록 돕는 일정 조율 서비스입니다.

### 해결할 핵심 문제

1. **조율 효율성:** 미응답, 조건부 가능, 반복 연락으로 회의 확정까지 수작업이 발생한다.
2. **참여 기회의 공정성:** 필수 참석자를 우선 고려하는 과정에서 일반 참석자가 소외될 수 있다.
3. **운영 신뢰성:** 응답 이후 일정이 변경되거나 외부 작업이 실패하면 회의 상태와 복구 방법이 불명확해진다.

# 4. 제품 정책 — 참석자 구분

## 4.1 용어 변경

기존:

- 필수 참석자
- 선택 참석자

개선:

- 일정 필수 참석자
- 일반 참석자

### 정의

**일정 필수 참석자**

회의 성립을 위해 일정 조건을 우선 충족해야 하는 참석자입니다.

**일반 참석자**

회의에 참여하도록 요청받으며, 가능한 시간을 최대한 반영해야 하는 참석자입니다.

### 필수 정책

- 참석자 분류는 사람의 중요도를 의미하지 않습니다.
- 일반 참석자의 의견과 일정도 추천에 반영합니다.
- 일정 우선순위와 발언권·조직적 가치를 연결하지 않습니다.
- 참석자에게 불필요한 우선순위 라벨을 노출하지 않습니다.
- 실제 의사결정 권한이나 참석 의무를 오해하게 해서는 안 됩니다.

# 5. 포용형 추천 알고리즘

AI는 자연어 조건 해석과 추천 결과 설명에 사용합니다.

실제 추천 후보의 필터링, 점수 계산, 확정 가능 여부는 결정론적인 서버 로직으로 검증합니다.

## 5.1 회의 성립 정책

MVP에서는 다음 두 가지를 지원합니다.

### A. 전원 참석 필요

모든 참석자의 일정 조건이 충족되어야 정상 확정할 수 있습니다.

### B. 일정 필수 참석자 우선

일정 필수 참석자의 조건을 충족하는 후보 중 전체 참석자의 참여 가능성을 최대화합니다.

기본 정책은 기존 PRD와의 호환성을 확인한 뒤 적용하고, 변경 시 마이그레이션 방안을 명시해주세요.

## 5.2 추천 단계

### 1단계 — 필수 조건 확인

- 회의 날짜
- 회의 길이
- 회의 성립 정책
- 일정 필수 참석자 가용성
- 참석 가능 정보의 최신성

필수 참석자가 명확하게 불가능한 후보는 정상 추천 대상에서 제외합니다.

### 2단계 — 참여 기회 최대화

필수 조건을 충족하는 후보에서 다음을 고려합니다.

- 전체 참석 가능 인원
- 일반 참석자 가용성
- 참석자 선호 시간
- 조건부 가능 여부
- 미응답 인원
- 확인 불가 인원

### 상태 처리 규칙

- 미응답을 가능으로 계산하지 않습니다.
- 캘린더상 충돌 없음은 참석 수락이 아닙니다.
- 조정하면 가능은 실제 조정 완료 전까지 가능으로 계산하지 않습니다.
- 확인 불가는 가능으로 계산하지 않습니다.
- 동률 후보는 동률로 표시합니다.
- 추천 점수와 확정 가능 여부를 분리합니다.

## 5.3 확정 전 참여 영향 안내

일부 참석자가 참석하기 어려운 후보를 선택하면 다음과 같이 안내합니다.

"이 시간에는 2명이 참석하기 어려워요. 모두 가능한 다른 후보가 있습니다."

단, 실제로 그런 대안 후보가 있을 때만 표시합니다.

# 7. 응답 유효성 관리

응답은 단순한 시간 선택이 아니라 날짜, 길이, 참석 방식 등 특정 조건에 대한 응답입니다.

회의 조건이 변경되면 영향을 받는 응답만 재확인해야 합니다.

| 변경 사항 | 기존 응답 처리 |
|---|---|
| 회의 제목 오탈자 | 유지 |
| 설명·참고 링크 수정 | 원칙적으로 유지, 중요한 변경은 안내 |
| 후보 추가 | 기존 후보 응답 유지, 새 후보 미응답 |
| 후보 날짜·시간 변경 | 변경된 후보 재확인 |
| 회의 길이 증가 | 영향을 받는 후보 재확인 |
| 온라인 → 대면 | 참석 가능 여부 재확인 |
| 장소 변경 | 이동 가능 여부 재확인 |
| 일정 필수 참석자 추가 | 기존 응답 유지, 확정 조건 재계산 |
| 회의 목적·역할의 중대한 변경 | 재확인 요청 지원 |

### 필수 구현 규칙

1. 응답을 무조건 삭제하지 않습니다.
2. 유효하지 않은 응답을 정상 가능으로 계산하지 않습니다.
3. 변경된 후보와 유지된 후보를 구분합니다.
4. 재확인이 필요한 참석자를 표시합니다.
5. 응답 유효성 판정은 서버에서 수행합니다.
6. 과거 응답 이력을 필요한 범위에서 보존합니다.

# 8. 회의 상태 모델

회의 상태를 하나의 '완료' 값으로 통합하지 마세요.

## 8.1 회의 상태

- 초안
- 응답 수집 중
- 확정 처리 중
- 확정됨
- 재조율 중
- 취소됨

재조율 중에는 기존 확정 일정과 새로운 제안 상태를 별도로 관리합니다.

## 8.2 외부 캘린더 상태

- 연결 안 됨
- 처리 중
- 반영됨
- 실패
- 최신 확인 불가

## 8.3 알림 상태

- 발송 대기
- 발송 중
- 발송됨
- 실패

알림 발송 성공을 실제 수신이나 열람으로 표시하지 않습니다.

## 8.4 회의실 및 링크 상태

실제 예약 또는 생성 기능이 존재하는 경우에만 적용합니다.

- 처리 전
- 처리 중
- 완료
- 실패

회의실 예약이 필수 조건이면 예약 실패 상태를 완료로 표시하지 않습니다.

# 9. 중복 요청 및 동시성 제어

## 9.1 응답 제출 중복 방지

다음 상황을 처리합니다.

- 제출 버튼 연속 탭
- 제출 직후 네트워크 끊김
- 동일 요청 재전송
- 다른 기기에서 같은 응답 수정

### 필수 규칙

- 서버에서 중복 요청을 식별합니다.
- 요청 처리 결과를 재조회할 수 있어야 합니다.
- 동일한 논리적 제출이 중복 생성되지 않아야 합니다.
- 제출 상태가 불명확하면 '전송 결과 확인 중'으로 표시합니다.
- 로컬 입력은 결과가 확인될 때까지 보존합니다.

버튼 비활성화만으로 중복 방지를 구현하지 마세요.

## 9.2 동시 확정 충돌 방지

공동 주최자 두 명이 서로 다른 후보를 동시에 확정하는 상황을 처리합니다.

### 필수 규칙

- 동일 회의 버전에서 유효한 확정 결과는 하나만 생성합니다.
- 확정 직전에 최신 응답을 재검증합니다.
- 먼저 확정된 결과를 다른 사용자에게 표시합니다.
- 이미 확정된 회의에 중복 초대를 발송하지 않습니다.
- 충돌 발생 시 변경자와 최신 상태를 확인할 수 있게 합니다.

서버의 트랜잭션, 버전 관리, 멱등성 제어를 활용해주세요.

# 10. 외부 작업 부분 실패 복구

회의 확정과 외부 캘린더 반영, 알림 발송은 별도 작업으로 관리합니다.

### 예시 상황

- NODI 내부 회의 확정 성공
- 캘린더 반영 실패
- 참석자 3명 중 2명에게 알림 발송 성공
- 1명에게 알림 발송 실패

### 사용자 안내

"회의는 확정됐습니다. 다만 일부 캘린더 및 알림 작업이 완료되지 않았습니다."

### 필수 규칙

- 성공한 작업을 불필요하게 반복하지 않습니다.
- 실패한 작업만 재시도합니다.
- 작업별 처리 결과를 저장합니다.
- 같은 외부 작업의 중복 실행을 방지합니다.
- 복구 중에도 회의 자체의 상태를 명확히 표시합니다.
- 실제 연동되지 않은 기능은 데모 상태로 구분합니다.

# 15. 시간대 및 회의 조건

시간은 실제 시점을 기준으로 안전하게 처리합니다.

- 날짜
- 시작 시각
- 종료 시각
- 시간대 식별자
- 참석자 현지 시간
- 자정 통과
- 서머타임 전환

시간대 변환 오류로 다른 실제 시점의 회의가 생성되지 않도록 검증합니다.

대면 회의의 장소 변경과 온라인 회의의 링크 변경은 응답 유효성에 영향을 줄 수 있습니다.

반복 회의는 초기 범위에서 제외할 수 있으며, 제외 시 UI와 기능 범위를 명확히 표시합니다.

# 19. 최종 실행 지침

다음 원칙을 반드시 지켜주세요.

1. 기존 NODI 브랜드와 디자인 스타일을 유지합니다.
2. 기존 코드베이스를 먼저 분석합니다.
3. 기존 기능을 불필요하게 삭제하지 않습니다.
4. 일정 필수 참석자와 일반 참석자의 참여 기회를 함께 고려합니다.
5. AI는 조건 해석과 설명에 활용하고, 추천 및 확정 검증은 결정론적 로직으로 처리합니다.
6. 응답 유효성과 데이터 최신성을 보장합니다.
7. 중복 요청과 동시 확정 충돌을 방지합니다.
8. 외부 작업의 부분 실패를 복구할 수 있도록 설계합니다.
9. 실제 구현되지 않은 연동을 성공으로 표시하지 않습니다.
10. 정상 흐름과 장애 흐름을 모두 검증합니다.
11. 사용자 입력과 기존 응답을 가능한 범위에서 보존합니다.
12. 완료·미완료·미검증 상태를 명확하게 보고합니다.

## 최종 목표

**NODI를 빠르게 시간을 추천하는 도구가 아니라, 참석자의 참여 기회를 존중하면서 회의 확정까지의 반복 업무와 운영 위험을 줄이는 신뢰할 수 있는 일정 조율 서비스로 완성해주세요.**

우선 현재 코드베이스를 분석하고, 구현 감사 문서와 단계별 실행 계획을 작성한 뒤, P0 안정성 개선부터 순차적으로 진행해주세요.
